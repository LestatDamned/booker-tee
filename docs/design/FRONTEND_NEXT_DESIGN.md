# Проектирование Frontend Next

Статус: **superseded SSR strategy / historical behavior reference**.

20 июля 2026 года React/API architecture заменила эту стратегию как target.
Новые workflows и shared abstractions в `src/app/web/` не добавляются. Активный
источник истины: [`REACT_FRONTEND_DESIGN.md`](REACT_FRONTEND_DESIGN.md). Текст
ниже сохраняет состояние и решения SSR-эксперимента на момент его остановки.

Текущее состояние реализации:

- зафиксирован baseline первого пилота в
  [`MANUAL_LEDGER_BASELINE.md`](MANUAL_LEDGER_BASELINE.md);
- создан изолированный presentation adapter `src/app/web/` со своими Jinja,
  CSS и небольшим общим слоем HTMX/Alpine.js;
- локальный стенд `/_next/foundation` проверяет shared-компоненты и UI-контракты;
- параллельный `/_next/ledger/manual` реализует list/edit-срез Этапа 3:
  workspace-scoped list, полные фильтры по периоду, поиску, типу, статусу,
  счёту, категории и объекту, pagination, target, деньги, metadata,
  readonly policy и `WorkbenchRow` на реальных application DTO;
- lazy edit загружается только для writer; HTMX сохраняет inline-панель,
  локальный `422` с draft и серверный выбор `replaceRow`/`replaceList`, а
  обычный HTTP использует отдельную full-page edit-форму и `303` после успеха;
- update response scope сохраняет фильтры и pagination: без фильтров и изменения
  даты заменяется одна строка, а при любом активном фильтре или изменении даты
  список, empty state, pagination и total заново строятся из БД;
- lazy create поддерживает income/expense/transfer и общий form contract с
  edit; HTMX использует inline-панель, локальный `422` и согласованный
  `replaceList` с OOB reset формы и total, а обычный HTTP — отдельную
  full-page create-форму;
- lifecycle manual operation реализован через отдельную action policy и явные
  cancel/restore/delete routes: HTMX заменяет row или list и возвращает
  локальный `422`, а обычный HTTP после успешной mutation выполняет `303` к
  списку без попытки воспроизвести inline-состояние; lifecycle business error
  без HTMX остается техническим JSON `422` fallback;
- query string разбирается толерантной `ManualLedgerUrlState`, которая хранит
  только URL-состояние списка; HTML-формы принимаются строковой Pydantic-моделью
  и преобразуются отдельными типизированными validation-моделями в commands;
- optimistic concurrency для manual edit реализован сквозным контрактом:
  `Operation.version`, скрытая версия формы, атомарный versioned update и
  локальный `409 Conflict`, который сохраняет draft и предлагает загрузить
  актуальную версию;
- финальный code audit пилота завершен; следующим инкрементом Этапа 3 остаются
  ручной smoke/performance check и canonical cutover manual ledger.

## 1. Решение

Booker Tee строит новый изолированный SSR-фронтенд параллельно с текущим
фронтендом. Текущий фронтенд рассматривается как источник знаний о продукте,
рабочих сценариев, найденных ошибок и визуальных экспериментов, но не как
кодовая основа нового интерфейса.

Новый фронтенд сохраняет текущий стек проекта:

```text
FastAPI + Jinja2 + HTMX + Alpine.js + проектный CSS
```

Это не переписывание на React/SPA и не второе финансовое приложение.

## 2. Архитектурная граница

Оба фронтенда используют один backend и одно финансовое ядро:

```text
Текущий web router -> общий application/service -> repository -> database
Новый web router   -> общий application/service -> repository -> database

Текущий web router -> текущий presenter -> текущий Jinja
Новый web router   -> новый presenter    -> новый Jinja
```

Общими остаются и не переписываются по визуальным причинам:

- доменные правила и финансовые инварианты;
- application use cases и сервисы;
- репозитории и SQLAlchemy-модели;
- аутентификация и workspace-авторизация;
- база данных и миграции;
- парсеры, импорт, дедупликация и логика проведения операций.

Новый фронтенд владеет только web presentation adapter: маршрутами страниц и
фрагментов, presenter и ViewModel, Jinja-шаблонами, CSS и небольшим UI
JavaScript. Новые маршруты напрямую вызывают общие use cases; они не вызывают
текущие HTTP-маршруты и не дублируют бизнес-правила.

Новые Jinja-шаблоны получают только подготовленные неизменяемые ViewModel. ORM-
модели, repositories, workspace membership и другие persistence/domain objects
не передаются в шаблон. Presenter принимает application DTO/read projection и
подготавливает видимые тексты, URL, разрешенные действия, статусы, деньги и
HTML-ID. Не создавать отдельный ViewModel для каждого декоративного `div`:
явные типы вводятся для устойчивых UI-контрактов.

## 3. Изоляция

Новый фронтенд должен быть изолирован от presentation assets текущего
фронтенда:

- его базовый шаблон не наследует текущий `base.html`;
- он не загружает текущий `static/css/app.css`;
- он не использует текущие template partials и legacy CSS-классы;
- текущий и новый renderers не выбирают шаблон через разбросанные по коду
  ветвления `if next_ui`;
- общий код между фронтендами допускается только ниже presentation boundary
  либо после того, как компонент стал принятой окончательной реализацией.

Новый frontend является отдельным SSR web-adapter. Он не размещается внутри
`src/app/features/*/presentation` и не создает там второй параллельный набор
presenters. Domain и application features остаются в `src/app/features/`, а
весь новый способ представления находится в `src/app/web/`.

Целевая структура:

```text
src/app/
├── features/                         # общий domain/application/backend
│   ├── ledger/
│   ├── imports/
│   └── accounts/
└── web/                              # новый SSR presentation adapter
    ├── router.py                     # подключает web feature routers
    ├── templating.py                 # изолированный Jinja environment
    ├── ui/                           # устойчивые общие UI-контракты
    ├── features/
    │   ├── ledger/
    │   ├── imports/
    │   └── accounts/
    ├── templates/                    # единственный Next template root
    │   ├── base.html
    │   ├── layouts/
    │   ├── components/
    │   └── features/
    └── static/
        ├── css/
        │   ├── app.css
        │   ├── settings/
        │   ├── themes/
        │   ├── foundation/
        │   ├── components/
        │   ├── features/
        │   └── utilities/
        └── js/
```

`web` является окончательным именем пакета, а не временным названием. Слово
`next` используется только для миграционного URL и тестовых маркеров. Это
позволяет в будущем добавить независимый `src/app/api/` и внешний frontend, не
смешивая JSON API schemas с Jinja ViewModel.

### 3.1 Web features и workflow-срезы

`src/app/web/features/` организуется по пользовательским workflow, а не по
глобальным техническим складам `presenters/`, `policies/` и `responses/`:

```text
src/app/web/features/ledger/
├── router.py
├── manual/
│   ├── routes.py
│   ├── queries.py
│   ├── presenter.py
│   ├── view_models.py
│   ├── action_policy.py
│   └── renderer.py
└── account_detail/
    ├── routes.py
    ├── presenter.py
    └── view_models.py
```

Структура прогрессивная. Простая feature может состоять только из `routes.py`
и конкретно названного `presenter.py`. Новый файл создается при появлении
самостоятельной ответственности, а не ради симметрии каталогов. Web workflow
не импортируют друг друга напрямую; устойчивые общие UI-контракты поднимаются
в `web/ui/` только после подтвержденного повторного использования.

Presenter получает application DTO/read projection, но не ORM-модель и не
repository. Jinja ViewModel не используется как будущая JSON API schema:

```text
application DTO/read projection
    -> SSR presenter -> Jinja ViewModel
    -> будущий API mapper -> JSON response schema
```

### 3.2 Шаблоны

Все новые Jinja-шаблоны находятся в одном изолированном template root:

```text
src/app/web/templates/
├── base.html
├── layouts/
├── components/
└── features/
    ├── ledger/manual/
    ├── imports/review/
    └── accounts/detail/
```

`components/` содержит только устойчивые общие компоненты. Feature partial
сначала остается в `templates/features/<feature>/` и переносится в общие
компоненты только при совпадении смысла, входного контракта и поведения.

### 3.3 CSS

Новый frontend подключает одну точку входа `web/static/css/app.css`. Она в
явном порядке импортирует модульные файлы из `settings/`, `themes/`,
`foundation/`, `components/`, `features/` и `utilities/`. На первом этапе не
добавляется Node.js или CSS build tool. При доказанном росте frontend entry
point можно разделить на bundles без изменения BEM-контрактов.

Компоненты используют семантические CSS tokens и не содержат жестко заданные
цвета конкретной темы. Первый набор значений предоставляет тема
`catppuccin-mocha`.

Во время разработки новый фронтенд использует явный префикс:

```text
/ledger/manual        -> текущий фронтенд
/_next/ledger/manual  -> новый фронтенд
```

Префикс нужен только для разработки и миграции. Он не является постоянной
частью продуктовых URL.

## 4. Текущий фронтенд как источник требований

Перед переносом каждого рабочего процесса фиксируется его наблюдаемый
контракт:

- отображаемые данные и форматирование;
- доступные действия и правила разрешений;
- пустое, загружающееся, ошибочное, readonly и lifecycle-состояния;
- HTMX-фрагменты и page-level HTTP fallback без обязательной inline parity;
- фильтры, pagination, anchors и поведение фокуса;
- responsive и accessibility требования;
- доменные инварианты, защищаемые рабочим процессом.

Текущий HTML и CSS не переносятся построчно. Зафиксированное поведение
реализуется заново на foundation нового фронтенда. Сохраняются только
осознанные продуктовые решения.

## 5. Вертикальная миграция и переключение

Рабочие процессы переносятся по одному:

```text
инвентаризация текущего поведения и потребителей
-> полная реализация процесса в новом фронтенде
-> добавление заменяющих тестов
-> проверка поведения и визуальных состояний
-> переключение канонического URL на новый фронтенд
-> удаление старого presentation-среза
-> финальные проверки
```

Не начинать широкую миграцию нескольких процессов, пока первый реальный
процесс не прошел переключение и очистку. Начальная последовательность:

1. Новый shell и ограниченный UI foundation.
2. Manual ledger как первый полный рабочий процесс.
3. Account detail/ledger как проверка повторного использования.
4. Проверка сложности foundation и оставшегося дублирования.
5. Остальные процессы в согласованном порядке.

Старый маршрут может временно остаться под `/_legacy/...` на один явно
оговоренный этап проверки. У него должно быть условие удаления; он не должен
стать вторым постоянно поддерживаемым фронтендом. Архивом служит история Git:
не хранить в production-коде файлы `*_old`, `*_legacy` или закомментированные
копии.

## 6. Контракт очистки

Для каждого переносимого процесса составляется cleanup manifest:

```text
старые маршруты и response renderers;
старые presenter и ViewModel;
старые шаблоны и partials;
feature-specific CSS-селекторы;
feature-specific Alpine/JavaScript;
тесты, которые нужно сохранить, адаптировать, заменить или удалить;
общие legacy-контракты и их оставшиеся потребители.
```

После переключения:

- удалить feature-specific presentation-код без оставшихся потребителей;
- удалить устаревшие template-тесты после появления заменяющего покрытия;
- удалить неиспользуемые импорты, селекторы, JavaScript hooks и partials;
- сохранять общий legacy-код только пока его использует другой текущий процесс;
- обновлять реестр потребителей после каждого среза;
- проверять удаленные имена поиском по репозиторию.

Общие legacy-контракты удаляются после последнего потребителя. Они не
копируются в новый фронтенд и не удаляются преждевременно.

## 7. Область согласованности HTMX-ответа

После изменения данных серверный presentation-router выбирает минимальную
область, которую нужно обновить для согласованного интерфейса. Клиентский
JavaScript и общий UI-компонент не пытаются вывести ее самостоятельно.

Стандартные режимы:

```text
replaceRow   -> заменить одну строку;
removeRow    -> удалить строку из текущего списка;
replaceList  -> заменить контейнер списка;
oobUpdate    -> обновить дополнительные feature-owned области.
```

Выбор зависит не только от типа действия, но и от текущих фильтров, pagination
и влияния результата на другие элементы. Обычный HTTP-сценарий после того же
действия выполняет redirect с сохранением безопасного контекста списка.
Create/edit без HTMX открываются отдельными полными страницами; обычный HTTP не
обязан воспроизводить inline-панель внутри строки списка.

Это page-level fallback, а не обещание полной работы интерфейса без JavaScript.
HTMX и Alpine.js остаются частью поддерживаемого Frontend Next runtime; обычные
ссылки, формы и `303` сохраняют понятную HTTP-навигацию и аварийный путь, но не
обязаны полностью повторять локальное интерактивное поведение без этих библиотек.

Ошибка валидации имеет HTTP-статус `422` и для обычного, и для HTMX-запроса.
Один глобальный обработчик нового frontend разрешает HTMX заменить целевой HTML
для ожидаемых `422` и `409`. Authorization errors, not-found и `5xx` не заменяют
существующий интерфейс через этот контракт. Feature-маршруты не возвращают
фиктивный `200` только ради HTMX swap.

Запросы синхронизируются локально в пределах формы или строки, а не через
глобальную очередь приложения. Во время mutation действие блокируется и
получает `aria-busy`; конкурирующее действие той же строки не запускается.
Финансовая корректность не зависит от JavaScript: для create/confirm/post/
transfer в каждом workflow проверяется необходимость server-side idempotency,
а lifecycle transitions защищаются транзакцией и доменными инвариантами.

Редактируемые сущности защищаются optimistic concurrency. Форма передает
невидимый integer `version`, а repository обновляет запись атомарно по условию
`id + version` и увеличивает версию после успеха. Несовпадение возвращает
`409 Conflict`: пользовательские изменения не перезаписывают актуальную запись,
а локальная форма объясняет конфликт и предлагает загрузить свежую версию.
Сложное визуальное сравнение версий не входит в первый этап.

### 7.1 Зафиксированный контракт Manual Ledger

Первый пилот применяет следующие конкретные правила:

- `ManualLedgerUrlState` отвечает только за толерантный разбор и каноническую
  сборку URL списка; открытые create/edit формы не являются состоянием URL
  списка;
- HTML form input сначала сохраняется строковой Pydantic-моделью без потери
  пользовательского draft, затем типизированная validation-модель преобразует
  значения в application command и локализованные field issues;
- HTMX загружает create/edit формы лениво и сохраняет локальное взаимодействие;
  без HTMX create/edit открываются отдельными полными страницами;
- успешный обычный create/update/lifecycle POST отвечает `303` и возвращает к
  безопасному контексту списка;
- create/update validation возвращает HTML `422`, optimistic conflict — HTML
  `409`; lifecycle business error без HTMX является ограниченным техническим
  JSON `422` fallback;
- без активных фильтров и изменения даты успешный update/status change заменяет
  строку; при активном фильтре или изменении даты весь список повторно читается
  из БД, поэтому SQL остается единственным источником истины для membership;
- create и delete всегда перестраивают список и связанные total/pagination
  области; feature-owned дополнительные области обновляются OOB-фрагментами;
- Alpine.js управляет только локальным disclosure/form state и не вычисляет
  финансовый смысл, permissions или область HTMX-ответа.

Финальный ручной smoke-check перед canonical cutover:

- [ ] создать доход, расход и перевод;
- [ ] проверить локальную ошибку для нулевой суммы и сохранение draft;
- [ ] изменить описание без фильтров и убедиться в замене одной строки;
- [ ] изменить операцию при активном фильтре и убедиться в обновлении списка;
- [ ] изменить дату и проверить новую позицию операции;
- [ ] воспроизвести optimistic conflict и загрузить актуальную версию;
- [ ] отменить, восстановить и окончательно удалить допустимую операцию;
- [ ] открыть create/edit прямыми URL без HTMX и проверить full-page формы;
- [ ] проверить desktop, `920px` и mobile без horizontal overflow;
- [ ] подтвердить readonly/permission поведение отдельным пользователем.

## 8. Технические детали в пользовательском интерфейсе

Обычные страницы нового фронтенда не показывают внутренние технические детали:

- UUID, database keys и внутренние имена сущностей;
- debug-состояния, HTTP-коды и названия обработчиков;
- имена parser, presenter, шаблонов и CSS-контрактов;
- необработанные исключения и внутренние payload;
- специальные блоки «Техническая информация».

Технические идентификаторы могут оставаться невидимыми в `id`, `name`,
`data-*`, URL и hidden fields, когда они нужны для HTTP, HTMX, accessibility или
тестового контракта. Это не делает их пользовательским содержимым.

Финансовая прослеживаемость сохраняется в понятной форме: пользователь может
открыть исходный документ, операцию или строку импорта, если это нужно для
проверки денег. Интерфейс показывает смысл и действие, а не внутренний UUID.
Диагностические подробности остаются в безопасных логах и development tools.

## 9. Поддерживаемые браузеры

Новый frontend ориентирован на актуальные современные Chromium-based browsers,
Firefox и Safari. Устаревшие браузеры, Internet Explorer и старые WebView не
поддерживаются.

Каждый переносимый workflow проходит автоматический UI audit в Chromium и
проверяется на desktop, `920px` и mobile viewport. Firefox проверяется на
контрольных этапах; Safari — когда доступна подходящая среда. Экспериментальные
browser API не используются без fallback. Отсутствие необязательного CSS-
эффекта не должно скрывать данные, состояние или действие.

## 10. Политика тестов

Новые тесты рефакторинга пишутся в `tests/ui_refactor/`. После завершения
рефакторинга владелец проекта решает, оставить, перенести или удалить эту папку.

Тесты повторяют workflow-структуру web-adapter и растут прогрессивно:

```text
tests/ui_refactor/
├── conftest.py
├── foundation/
├── contracts/
└── features/
    ├── ledger/manual/
    ├── imports/review/
    └── accounts/detail/
```

Простой workflow начинает с одного связного test module. Он делится на
presenter, HTTP и permission tests только при появлении разных историй.
Универсальные fixtures находятся в корневом `conftest.py`, а feature-specific
fixtures — рядом с ближайшим общим владельцем. Имена fixtures описывают
финансовое или UI-состояние, а не называются `data`, `item` или `result`.

Существующие тесты классифицируются для каждого процесса:

| Что проверяет тест | Действие |
| --- | --- |
| Домен, финансовый инвариант, workspace, безопасность | Сохранить |
| Полезное HTTP-поведение, связанное с текущим renderer | Адаптировать к новому фронтенду |
| Presentation-поведение, покрытое новым контрактным тестом | Заменить |
| Точные устаревшие классы, wrappers и имена partials | Удалить после переключения |
| Временное сравнение текущего и нового фронтенда | Удалить вместе с текущим процессом |

Тест не удаляется только потому, что он упал после переписывания. Он удаляется,
когда его контракт устарел или существует заменяющее покрытие.

Обязательные проверки перед переключением:

- сфокусированные тесты нового UI;
- затронутые feature/domain тесты;
- workspace- и permission-проверки;
- HTMX и обычные HTTP-сценарии;
- существующий visual/UI audit, где он применим;
- Ruff и ty для измененного Python-кода;
- поиск по репозиторию, подтверждающий удаление feature-specific legacy-имен.

Для каждого workflow используется легкий многоуровневый quality gate:

```text
Presenter/ViewModel contract tests;
HTTP и HTMX response tests;
permission/workspace tests;
сохраненные financial/domain tests;
существующий Chromium UI audit;
короткий ручной visual checklist;
performance baseline.
```

Существующая инфраструктура запускается релевантным сценарием, например:

```bash
uv run python scripts/ui_audit.py --scenario realistic
uv run python scripts/ui_audit.py --scenario review_interactions
uv run python scripts/ui_audit.py --scenario design_audit
```

Не создавать snapshots полного HTML, pixel-perfect screenshot test для каждого
состояния, E2E-тест на каждый CSS modifier или полную browser-матрицу на каждый
commit.

Performance baseline первого пилота фиксирует как минимум:

- количество и характер database queries без нового N+1;
- размер HTML репрезентативного списка;
- отсутствие заранее отрендеренных edit forms в закрытых строках;
- размер нового CSS и отсутствие feature-specific дубликатов;
- отсутствие глобального Alpine/JavaScript controller на каждую строку.

Абстрактный лимит заранее не устанавливается. Следующий workflow не должен
необъяснимо ухудшать baseline первого пилота.

## 11. Правило объема кода

Временный рост кода во время параллельной работы двух фронтендов ожидаем. После
очистки каждого процесса не должно оставаться двух production-реализаций одного
presentation-поведения. Необъяснимый рост production-кода требует повторного
design review. Тесты и явные ViewModel оцениваются по пользе и связанности, а не
только по количеству строк.

Рукописный Python-код держится в читаемой середине. При приближении модуля к
`250-350` строкам проверяется его связность; модуль не должен незаметно
разрастаться за `500` строк. Это сигнал для review, а не механический лимит и не
цель. Файл разделяется, когда рассказывает несколько историй или имеет несколько
причин для изменения. Не заменять один связный модуль десятью файлами примерно
по сто строк, если для понимания сценария между ними приходится постоянно
переключаться.

Предпочтительны actor-oriented API с понятной формой `Кто.что_делает`:

```text
ManualLedgerPresenter.present(...)
ManualOperationActionPolicy.resolve(...)
ManualLedgerPageQuery.execute(...)
ManualLedgerEditQuery.execute(...)
ManualLedgerRenderer.row(...)
MoneyFormatter.format(...)
```

Свободные функции остаются уместны для маленьких чистых predicates,
форматирования, normalization, framework callbacks и расчетов без собственного
действующего участника. Не создавать класс только ради запрета свободной
функции.

Имена должны раскрывать роль кода. Не использовать без ясной локальной причины
абстрактные `Manager`, `Processor`, `handle`, `data`, `helpers.py`, `utils.py` и
аналогичные имена. Импорты явные и идут из определяющего модуля; wildcard,
широкие package re-exports и скрытая регистрация через import side effects не
используются.

Переиспользуется одинаковый устойчивый смысл и контракт, а не просто похожие
строки кода или HTML. Feature-specific реализация остается локальной, пока
общая ответственность не подтверждена повторным применением.

## 14. Реестр принятых решений

Опрос по углубленному аудиту завершен. Приняты следующие решения:

1. Мигрированный workflow независим от current frontend; общий legacy удаляется
   после последнего потребителя.
2. Новый UI foundation и frontend строятся с нуля в изолированном SSR-слое;
   backend и финансовое ядро остаются общими.
3. Сервер выбирает `replaceRow`, `removeRow`, `replaceList` или `oobUpdate` по
   области согласованности.
4. Расположение действий задает `ActionSetVM`; отдельной technical-группы нет.
5. Действия представлены явными `LinkActionVM`, `SubmitActionVM` и
   `DisclosureActionVM`. HTMX поддерживает inline-взаимодействие, а обычный
   HTTP использует page-level fallback: отдельные create/edit страницы и
   redirects после mutations без обязательной inline parity.
6. `row_id` идентифицирует отображаемую запись, а бизнес-ссылка хранится
   отдельно.
7. `OperationType` и направление `MoneyEntry` являются двумя разными
   серверными значениями.
8. Jinja получает только подготовленные неизменяемые ViewModel, не ORM-модели.
9. Validation error возвращает `422`; stale write возвращает `409`; оба ответа
   поддерживают локальный HTMX swap.
10. Edit panels независимы; закрытие сохраняет draft, «Отмена» сбрасывает его.
11. Запросы синхронизируются локально, а критичные финансовые mutations получают
    server-side гарантию от повторного результата.
12. Отсутствующая targeted row временно закрепляется сервером без изменения
    фильтра и pagination count.
13. После удаления или замены общий helper детерминированно восстанавливает
    фокус.
14. Редактируемые сущности используют optimistic concurrency с integer
    `version`.
15. Поддерживаются актуальные Chromium, Firefox и Safari без старых браузеров.
16. Каждый workflow проходит легкий quality gate и baseline, без тяжелой новой
    visual/E2E-инфраструктуры.
17. Frontend Next является отдельным SSR adapter в `src/app/web/`; backend,
    domain и application остаются в `src/app/features/`.
18. Пакет сразу получает окончательное имя `web`; `_next` остается только
    временным URL prefix и миграционным маркером.
19. Все новые Jinja templates находятся в одном root
    `src/app/web/templates/` и разделены на общие components и feature
    namespaces.
20. CSS состоит из модулей с одной точкой входа
    `src/app/web/static/css/app.css`; новый build tool не вводится.
21. Python-код web features организуется прогрессивными вертикальными
    workflow-срезами, а не глобальными техническими каталогами.
22. Простой route может вернуть шаблон напрямую; сложный экран разделяет
    screen-specific `*Query`, чистый Presenter и узкий workflow-specific
    `*Renderer`. Query возвращает application/read DTO без HTTP и ViewModel,
    Renderer не обращается к session, сервисам или финансовой логике.
23. `tests/ui_refactor/` повторяет workflow-структуру web-adapter и содержит
    отдельные `foundation/` и `contracts/`; тестовые файлы разделяются только
    по реальным ответственностям.
24. URL-state списка и form-state не смешиваются: query string разбирается
    толерантной Pydantic-моделью, а create/edit без HTMX используют отдельные
    страницы.
25. HTML form input сохраняется строковой Pydantic-моделью, после чего отдельная
    типизированная validation-модель строит application command или
    локализованные field issues.
26. При любом активном фильтре mutation перестраивает manual-ledger list из БД;
    Python response policy не повторяет SQL-предикаты repository.
27. Полноценный page-level fallback обязателен для create/edit и успешных
    mutations; lifecycle business errors без HTMX могут оставаться техническим
    JSON `422` fallback до появления общего flash/error-page контракта.

Дополнительное обязательное решение: обычный пользовательский интерфейс не
показывает UUID, database keys, debug-состояния и специальные блоки технической
информации. Финансовая прослеживаемость сохраняется понятными ссылками и
действиями.
