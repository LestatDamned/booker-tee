# Этап 3. Итог и действия справа

Статус: completed.

## Цель

Сначала показать будущий или уже созданный финансовый результат, затем дать
действие над ним.

## Scope

- Для income/expense показывать тип, сумму, категорию и объект при наличии.
- Для transfer показывать будущий или созданный маршрут счетов.
- Для confirmed строки показывать `Проведено` и итог созданной операции.
- Основные действия: `Подтвердить`, `Изменить`; редкие действия — ниже по
  иерархии.
- Не оставлять action rail пустым, если результат уже известен.

## Критерии готовности

- [x] Рядом с CTA однозначно видно, что будет создано.
- [x] Auto-applied confirmable suggestion имеет быстрый primary confirm.
- [x] Confirmed строка показывает не только статус, но и результат.
- [x] Primary, secondary и danger действия не конкурируют.
- [x] Readonly mode не обещает недоступные действия.

## Реализовано

- action rail строится в порядке `итог → primary → secondary → ещё действия`;
- income/expense/adjustment показывают тип, форматированную сумму, категорию и
  объект;
- transfer показывает направление и явно сообщает о незаполненном втором
  счёте;
- outcome использует естественные формулировки `Будет создан расход`,
  `Создан доход`, `Создан перевод`;
- абсолютная сумма результата показана отдельной строкой без разделителя `·` и
  без знака; знак сохраняется у исходного движения в основной части строки;
- карточка результата использует слабый семантический фон и боковой акцент для
  income, expense, transfer и adjustment, а текст остаётся обязательным
  носителем смысла;
- confirmed outcome не дублирует статусный бейдж `Проведено`;
- terminal ignored/duplicate/failed строки не обещают создание операции;
- outcome остаётся доступен в readonly-режиме, мутационные действия скрыты.

Точные названия обоих счетов уже проведённого перевода требуют отдельного поля
в API DTO и остаются частью этапа 8. До этого интерфейс не конструирует и не
угадывает название второго счёта.
